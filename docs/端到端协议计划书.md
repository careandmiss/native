# 端到端协议计划书 — native_fill → ppt-master

> 目标：把 **markdown 内容 + PPT 模板** 一键产出符合模板原生设计的 PPTX，全程不依赖手工修 SVG。
> 适用范围：本文档对应 `mcp_ppt_native_fill`（`D:\Code\tst\native_fill\src\mcp_ppt_native_fill\`）。
> 关联：`docs/ppt生成流程.md`（ppt-master 手工路径复盘）｜ `docs/ppt生成流程.md §6` 4 条硬约束来源

---

## 0. 目标与范围

### 0.1 终极功能（一句话验收）

给定：

- `markdown_path`：任意 `*.md`（含 H1/H2/段落/表格/列表）
- `template_pptx_path`：任意原生模板（含可见文本框 + 可编辑 shapes）
- 可选：`outline_hint`（章节顺序、archetype 偏好、色板）

输出：

- `output.pptx`，页数 = markdown 章节数 + 模板原生前后页（封面/目录/结束）
- 视觉与模板 1:1 还原（不被新卡覆盖原色板、不打断原 chrome）
- 9 条 PR 改进全部生效：自动注入元数据、preflight、容错 fallback、chrome 注入等
- 失败有可读回执：`{ok, stage, warnings, errors, export_summary}`

### 0.2 In scope / Out of scope

| In scope | Out of scope |
|---|---|
| PPTX → SVG → PPTX 全自动 roundtrip | PPT 模板**创建**（走 ppt-master `create-template` 路由） |
| LLM 拆大纲（planner）+ 模板自适应 | 配图生成 / 图片检索 |
| 4 类硬约束的自动规避 + 离线预检 | PowerPoint 动画 / 切换效果 |
| 失败重试 + auto-fix + 容错降级 | Office 365 在线模板 |
| Chrome（topbar / footer）智能注入 | 模板母版（Master / Layout）创建 |
| LLM 不可用时的纯 deterministic 回退 | 模板原始母版的 chrome 移除 |

### 0.3 非终极承诺

- **不保证**生成结果 LLM-determined（每次 LLM 调用可能产出略有差异）
- **不保证**100% 还原原模板的字体/字号（只保证不破坏）
- **不保证**模板形状 id 100% 识别（失败的 shape 会被记录在 warnings）

## 3. 各阶段详细说明

### 3.1 阶段 1 — Workspace Init

**入口**：`run_with_mapping(workspace, source_pptx, output_pptx, ..., clean_workspace=False)`

**职责**：创建 workspace 目录结构、可选清旧。

**文件布局**（workspace 为根）：

```
workspace/
├── authoring-svg-flat/       ← SVG 中间产物
│   ├── slide_01.svg .. slide_NN.svg    ← 模板 skeleton
│   ├── slide_partNN_div.svg            ← 阶段 2.6 克隆
│   ├── slide_partNN_content.svg        ← 阶段 2.6 克隆
│   ├── slide_partNN_toc.svg            ← smart TOC 克隆
│   └── authoring_summary.json          ← 阶段 2 写入
├── page_plan.json            ← 阶段 3 写入
├── validation/
│   ├── <output>.delivery.json ← 阶段 5 写入
│   └── readback.md           ← 阶段 5 写入
└── image_assets/             ← 阶段 2 自动抽取（可选）
```

### 3.2 阶段 2 — PPTX → SVG roundtrip

**入口脚本**：`${ppt-master}/scripts/pptx_to_svg.py --roundtrip`

**入口函数**：`runner.run_pptx_to_svg(skill_dir, source_pptx, workspace, inheritance_mode="both")`

**产物**：
- `authoring-svg-flat/slide_01.svg ... slide_NN.svg`（每个 PPTX slide 一个）
- `authoring_summary.json`（shape_index / skeleton_index / 字体 / frame）
- `image_assets/`（图片资源，ppt-master 自动抽取）

**闸门**：
- 必须 exit=0，否则 `state.stage = "failed"`
- 必须写出 ≥1 张 `slide_*.svg`

### 3.3 阶段 2.5 — LLM Planner（opt-in）

**入口函数**：`llm_planner.plan_content_mapping(md_path, workspace, layout_hints=None)`

**触发条件**：调用方传 `enable_llm_planner=True` 且 `content_markdown` 非空

**输入**：
- `shape_index`（阶段 2 产物的索引）
- `skeleton_index`（slide 角色识别：cover / toc / divider / content / ending）
- `content_markdown`（用户源文档）
- `layout_hints`（archetype 偏好，如 `{"prefer": ["hero_statement", "kpi_row"]}`）

**输出（PlannerResult）**：
- `content_mapping`：`{"slide_04.svg": {"shape-23": "新文字"}}`
- `page_plan_additions`：超出模板 N 张 content 时，新增 cloned pages
- `new_blocks`：每张内容页的 archetype 布局（layout: 3-column-cards / flow-steps / revision-table / hero_statement / kpi_row ...）
- `skeleton_kind`：slide_NN.svg → role

**容错（关键）**：
- LLM 调用失败 → 自动降级为 deterministic A-path / E-path（Phases 4）
- LLM 返回空 mapping → fallback 到 caller_mapping（如果有），否则展开规划器自己出
- 网络错误 → 记 warning，继续按 caller_mapping 走

### 3.4 阶段 2.6 — Plan Realize

**入口函数**：`realize_plan(state, caller_page_plan=None, caller_new_blocks=None)`

**职责**：把 PlannerResult 落到磁盘 SVG。

**子步骤**：
1. `_seed_original_roster`：从 workspace 现存 slide_*.svg 提取 cover/toc/divider/content/ending，**Bug #1 fix**：ending 移到队尾
2. 对每个 `page_plan_addition`：
   - `shutil.copy2(skeleton, new_svg)` 克隆
   - `svg_edits.apply_text_edits(new_svg, edits)`
3. 对每个 `new_block`：折叠到 `state.context["new_content_blocks"]`
4. **Bug #2 fix**：cloned 但缺 body 的 content 页补 `new_blocks`（避免大块空白）
5. **Bug #1 fix（ending）**：把 `kind == "ending"` 的 svg 移到 final_pages 末尾
6. `autofix.repair_workspace_svgs` 预修复克隆的 vendor XML quirks

**闸门**：cloned SVG 必须写出；缺 skeleton 时记 warning 不 fail

### 3.5 阶段 3 — SVG Authoring（核心渲染层）

**入口函数**：`phase3_author(state, page_plan_pages, content_mapping, new_content_blocks)`

**子步骤**：

| # | 子步骤 | 归属 | 输出 |
|---|---|---|---|
| 3a | `write_page_plan` | `pipeline.write_page_plan` | `page_plan.json` |
| 3b | `apply_text_edits` per svg | `svg_edits.apply_text_edits` | text 替换 |
| 3c | `_remove_empty_toc_slots` | `pipeline._remove_empty_toc_slots` | 删空 TOC 行 |
| 3d | `_remove_existing_new_content_group`（idempotency） | `pipeline._remove_existing_new_content_group` | 防 duplicate id |
| 3e | `_render_new_block(spec)`（**PR-1 注入元数据**） | `block_renderer.render_new_block` | 内层 SVG 片段 |
| 3f | `write_new_content_block` | `svg_edits.write_new_content_block` | 完整 `<g>` 入 svg |
| 3g | `_inject_content_chrome`（Phase 11） | `chrome.render_chrome_topbar/footer` | topbar + footer |
| 3h | `_strip_template_chrome_shapes("shape-22")`（Phase 12） | `svg_edits.strip_template_chrome_shapes` | 删原 chrome 避免冲突 |

**PR-1 注入点（block_renderer.render_new_block）**：
- **P1 自动去重**：`renumber_duplicate_ids` 给重复 svg id 加 `-N` 后缀
- **P2 自动补 shape-id/scope**：`<g data-pptx-object="picture">` 自动加 `data-pptx-shape-id` + `data-pptx-shape-scope`
- **P3 自动去掉多余 text**：semantic shape 多 text 时自动剥 marker
- **P4 自动拆 single-child group**：单子 wrapper 提升为顶层

### 3.6 阶段 3.5 — Pre-export Normalize

**入口函数**：`normalize_export_artifacts(state, source_pptx, disabled=())`

**3 个独立修复组（按 disabled tuple 可单独 opt-out）**：

| 修复组 | 触发条件 | 函数 |
|---|---|---|
| `render_compat` | 默认 | gradient / picture_structure / unsafe_font |
| `connector_preserve` | 默认 | zero-stroke → 1（否则 vendor 丢弃） |
| `source_ref` | 默认 | strip invalid `data-pptx-source-ref` |

**判定逻辑**：
- `edited_slides = edited_svg_paths ∪ content_mapping.keys ∪ baseline_diff`
- edited slide → strip **所有** source-ref（让 vendor 走 fresh render 路径）
- unedited slide → 只 strip 指向不存在 slide 的 ref
- `render_compat in disabled` → 全部 strip（bypass mode）

**boteng 例外**：`fix_nested_picture=True` + `skip_phase3_5=True` 走全 bypass

### 3.7 阶段 4 — Quality Gate + Auto-fix Loop

**入口函数**：`phase4_quality(state, auto_fix=True, max_fix_iterations=3, strict=True)`

**子步骤**：
1. `autofix.repair_workspace_svgs`：vendor XML quirks
2. `autofix.restore_shape_attrs`：data-pptx-* attrs 兜底
4. `runner.run_svg_authoring_view_refresh`：vendor view 缓存刷新
5. 循环（最多 max_fix_iterations）：
   - `runner.run_svg_quality_check`（vendor 质检）
   - 失败 → `autofix.run_autofix_round`
   - 成功 / 修复规则全部用完 → 退出
6. `strict=True` 失败 → `state.stage = "failed"`
7. `strict=False` 失败 → `state.stage = "quality_advisory"`，**不阻断**阶段 5

**boteng 默认**：`strict=False`（vendor QC 对 boteng 的"非 PPT 安全字体"等发 WARN，但不真的阻断 svg_to_pptx）

### 3.8 阶段 5 — Export + Delivery

**入口函数**：`phase5_export(state, output_pptx, validate_strict=True)`

**子步骤**：
1. `autofix.restore_shape_attrs`：最后一次兜底
2. `runner.run_svg_to_pptx --roundtrip`：主导出
3. `runner.run_pptx_delivery_check`：交付闸门（ZIP 完整性 / slide 数 / shape 一致性）
4. `validate_strict=True` + status=failed → `state.stage = "failed"`
5. `runner.run_source_to_md`：产出 `readback.md`，方便人工对照

**最终回执 `_finalize(state)`**：
```json
{
  "ok": true,
  "stage": "done",
  "workspace": "...",
  "output_pptx": "...",
  "duration_ms": 12345,
  "fix_iterations": [...],
  "warnings": [...],
  "errors": [],
  "llm_content_mapping": {...},
  "export_summary": {...},
  "delivery": {"status": "passed", "zip_integrity": "ok",
               "slides_count": 13, "advisories_count": 0},
  "readback_md": "validation/readback.md"
}
```

## 6. 失败处理矩阵

| 失败位置 | 行为 | 可恢复？ |
|---|---|---|
| G1 attribution_guard | 立刻 fail，禁止重试 | ❌ |
| G2 roundtrip | fail，归因到 PPTX 模板本身 | ❌ |
| G3 preflight（**图像化建议**） | 警告 + 在 PR-12 后变成 fail-fast | ✅（修复 SVG） |
| G4 page_plan schema | fail（schema 不合规是 bug） | ❌ |
| G5 unknown shape_id | warning + skip（≠ fail） | ✅（去掉 edit） |
| G6 bad bounds | warning + skip | ✅ |
| G7 vendor QC | auto-fix 循环 ≤3 次；耗尽则 strict fail | ✅ |
| G8 svg_to_pptx | fail，归因到 vendor 兼容性 | ⚠️（disable autofix 重试） |
| G9 delivery | fail，归因到 roundtrip 完整性 | ⚠️ |

**降级路径**：
- G7 失败 + `strict=False` → 继续 G8 + G9
- G8 失败 → 检查是否是 source-ref 问题 → 重跑时 `disabled=("source_ref",)` bypass
- G8 失败 + nested picture → `fix_nested_picture=True` + `skip_phase3_5=True`
- LLM 失败 → 自动走 deterministic fallback（A-path / E-path）

## 9. 开放问题

1. **boteng nested-SVG picture workaround**：`fix_nested_picture=True` 是 boteng 模板的特殊解法。需要一份"模板分类器"自动决定是否开启。
3. **LLM 调用的成本/时延**：每次 markdown → PlannerResult 一次 LLM 调用 + 大 prompt。boteng markdown ~3k 字符，prompt ~8k 字符。是否值得本地小模型化？
4. **chrome 注入对模板原 chrome 的取舍**：boteng 模板的 chrome 在 shape-22（左上角），我们注入的 chrome 在 topbar。Phase 12 已删除 shape-22，但是否对所有模板都该删？需要一份"模板 chrome 调查清单"。
5. **PR-12 强 fail 后是否影响确定性回退**：G3 失败时 deterministic fallback 还能救场吗？需要测试。
6. **PR-13 before/after 视觉 diff**：当前只渲染 post-roundtrip SVG，没有 vis-on before 对比（需 LibreOffice 渲染原模板 PPTX，本环境无 LibreOffice）。Wave 3 评估是否需要。
7. **DOCX/PDF 导出**：现状只产 PPTX。是否需要中间产物给人工？
8. **PR-11 LLM 不可用时回退**：当前 generate_pptx LLM 失败时 `pipeline.llm_plan` 静默吞掉错误继续，导出 PPTX 但页面空白。需要给一个清晰的"LLM 未连接"错误提示。
